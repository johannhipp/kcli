# v0.1 scope: local marketplace discovery and messaging

Status: planned
Target version: `0.1.0`

## Product goal

v0.1 exposes a focused set of Kleinanzeigen browser capabilities through an
agent-friendly CLI: discover listings, inspect all decision-useful listing and
seller information, and—after logging in—read and send messages.

It is not a selling tool, shipping tool, payment tool, or autonomous purchasing
agent. The target use case is people who independently arrange an in-person
pickup and pay on the spot, but those details remain ordinary user-written chat
content. kcli never creates or manages listings, interprets an agreement, or
participates in a platform or offline transaction.

### CLI product rule

Every v0.1 feature must correspond to something the user can see or do in the
Kleinanzeigen browser experience. kcli exposes those primitives in a form that
agents can call reliably; it does not invent higher-level marketplace workflows.

The intended command families are:

- `search` and `filters` for discovery;
- `listing` for listing data, media, and public links;
- `seller` for seller data and explicitly best-effort lookup;
- `auth` for login status, interactive login, refresh, and logout;
- `dm` for listing, reading, starting, replying, and marking read.

The exact proposed spellings and flags are maintained in
[`command-syntax.md`](command-syntax.md). `dm poll` and `dm watch` are also in
v0.1: both use the same incremental polling core, while `watch` keeps it running
and emits NDJSON events. There is no known upstream push endpoint.

Commands must support non-interactive arguments, structured JSON, stable IDs,
useful exit codes, and clear dry-run or confirmation behavior where applicable.
There are no `pickup`, `meeting`, `negotiate`, `pay`, or `transaction` commands.

## Release boundary

### Anonymous discovery

v0.1 supports:

- keyword, category, location, radius, price, offered/wanted, picture-required,
  pagination, and supported sort modes;
- every category-specific filter advertised by
  `/api/ads/search-metadata/{category_id}.json`, including enum, boolean, and
  range-like filters when the service describes them;
- combining, clearing, and serializing filters so a search can be reproduced;
- client-side exclusions over title and description;
- structured and human-readable search results;
- direct listing lookup by listing ID or public URL.

“All filters” means all filters discoverable from the mobile metadata contract,
not filters guessed from website labels or hard-coded once. Unknown filter types
must be retained in raw metadata and reported as unsupported rather than ignored.

### Complete listing inspection

For an available listing, v0.1 presents and preserves:

- ID, title, description, public URL, category, listing/ad type, status, labels,
  posting/edit timestamps, and view count when returned;
- price amount and price type;
- location label, postcode, approximate coordinates, distance, and pickup or
  shipping indicators when returned;
- every category attribute, including unknown attributes;
- every returned image and media link, its relation/size label, and optional
  controlled image download;
- poster type, seller account type, public contact/display name, user ID,
  account age, aggregate rating, badges, and company information when returned;
- both a stable normalized representation and a redacted raw-payload escape
  hatch so new fields are not silently lost.

A missing or deleted listing is normal marketplace state. The client reports it
as unavailable and does not retry it as an outage.

### Seller discovery

The official free website does not provide a global username directory, and the
selected mobile client has no public endpoint for arbitrary seller-name search.
Accordingly, v0.1 supports:

- resolving a seller from a known listing ID or listing URL;
- accepting a known seller/user ID or public profile/company URL;
- indexing public seller identities encountered in search and detail results;
- exact and case-insensitive partial search over that local seller index;
- showing the seller's public metadata and any other public listings that can be
  reached from known listing/profile links;
- labeling every seller result with its source and completeness.

Seller-name results are explicitly best-effort and cannot claim global coverage.
The CLI must say when it searched only locally encountered sellers. Discovering
an official or mobile global people-search interface is not part of v0.1.

### Authenticated messaging

After an interactive Auth0 PKCE login, v0.1 supports:

- operating-system-secret-store token persistence, refresh, local logout, and
  clear expired/revoked-token errors;
- listing conversations with unread state and listing/counterparty context;
- opening a conversation and reading its complete available message history;
- replying with plain text to an existing conversation;
- starting a conversation from a listing and sending the first plain-text
  message;
- marking conversations read;
- retaining listing and seller context beside messages even if the listing later
  becomes reserved or unavailable.
- running one bounded incremental synchronization cycle with a resumable local
  cursor, list-only by default so polling does not mark a conversation loaded;
- watching for newly observed DM events as a foreground NDJSON stream built over
  conservative list-only polling, with conversation opening available only as
  an explicitly state-touching option.

Every outbound message requires a visible preview and explicit confirmation,
and confirmation resupplies the exact text whose digest was previewed.
There is no unattended or bulk messaging in v0.1. Attachments, templates,
blocking, reporting, and conversation deletion are deferred.

### Conversation content is opaque

kcli sends and returns message text. It does not parse, classify, validate, or
act on statements about availability, price, inspection, pickup, meeting place,
or payment. It does not maintain separate state for an agreement and does not
turn chat text into follow-up actions.

## v0.1 user stories

Every scoped story uses the same format as the long-term inventory:

> **V01-ID** — As a **role**, I want **a capability or outcome**, so that **I
> receive a clear benefit**.

### Search and filters

- **V01-SEARCH-01** — As a visitor, I want to search by keyword or browse without a keyword, so that I can discover relevant listings.
- **V01-SEARCH-02** — As a visitor, I want to restrict a search to any category, so that unrelated listing types are excluded.
- **V01-SEARCH-03** — As a visitor, I want to resolve a place or postcode and choose a radius or all Germany, so that geographic coverage matches my pickup range.
- **V01-SEARCH-04** — As a visitor, I want to filter by price, offered/wanted type, and picture availability, so that basic listing requirements are enforced.
- **V01-SEARCH-05** — As a visitor, I want to use every filter and value advertised for the selected category, so that category-specific searches are not artificially limited.
- **V01-SEARCH-06** — As a visitor, I want to combine, remove, and inspect active filters, so that I understand exactly why a result matched.
- **V01-SEARCH-07** — As a visitor, I want to sort by supported date, price, or distance modes, so that useful results appear first.
- **V01-SEARCH-08** — As a visitor, I want to paginate and deduplicate results, so that I can inspect the complete result set reliably.
- **V01-SEARCH-09** — As a visitor, I want to exclude listings containing unwanted terms, so that obvious mismatches can be removed locally.
- **V01-SEARCH-10** — As an agent user, I want structured JSON and a reproducible search specification, so that a search can be inspected or rerun safely.

### Listing inspection

- **V01-LISTING-01** — As a visitor, I want to open a listing by ID or public URL, so that I can inspect a known offer directly.
- **V01-LISTING-02** — As a visitor, I want all returned identity, description, category, price, status, location, date, and attribute fields, so that I can evaluate the offer without losing information.
- **V01-LISTING-03** — As a visitor, I want to view every returned image and media variant, so that I can judge the item's condition visually.
- **V01-LISTING-04** — As an agent user, I want to download selected listing images to an explicit destination, so that they can be reviewed or processed locally.
- **V01-LISTING-05** — As a visitor, I want pickup, shipping, seller-type, rating, badge, and company signals clearly separated from the seller's prose, so that factual metadata is easy to assess.
- **V01-LISTING-06** — As an agent user, I want normalized data plus a redacted raw response, so that new private-API fields remain inspectable without exposing secrets.
- **V01-LISTING-07** — As a visitor, I want unavailable, expired, reserved, and deleted states reported clearly, so that I do not act on stale inventory.
- **V01-LISTING-08** — As a visitor, I want a stable public link in every result, so that I can verify the listing in the official website.

### Seller discovery

- **V01-USER-01** — As a visitor, I want to resolve the seller attached to a known listing, so that I can inspect the counterparty before contacting them.
- **V01-USER-02** — As a visitor, I want to look up a seller from a known user ID or public profile/company URL, so that I can return to a seller I already know.
- **V01-USER-03** — As a visitor, I want to search encountered sellers by exact or partial display name, so that I can rediscover a seller without remembering an ID.
- **V01-USER-04** — As a visitor, I want to see seller account type, account age, ratings, badges, company information, and known public listings, so that I can assess relevance and trust.
- **V01-USER-05** — As an agent user, I want every seller result labeled as direct, linked, or locally indexed and complete or best-effort, so that I do not mistake local discovery for a global user search.

### Authentication and DMs

- **V01-DM-01** — As a member, I want to log in through the interactive PKCE flow and refresh or clear my local session, so that account access remains controlled.
- **V01-DM-02** — As a member, I want to list conversations with unread and listing context, so that I can see which DMs need attention.
- **V01-DM-03** — As a member, I want to read the complete available history of a conversation, so that I understand prior context before responding.
- **V01-DM-04** — As a member, I want to preview and explicitly confirm a plain-text reply, so that no message is sent accidentally.
- **V01-DM-05** — As a buyer, I want to preview and explicitly confirm the first message on a listing, so that I can contact its seller safely.
- **V01-DM-06** — As a member, I want to mark a conversation read, so that unread state reflects what I reviewed.
- **V01-DM-07** — As a member, I want listing and counterparty context preserved when a listing becomes unavailable, so that an existing pickup arrangement remains understandable.
- **V01-DM-08** — As a member, I want authentication, rate-limit, and message-send failures reported without blind retries, so that duplicate communication and account risk are avoided.
- **V01-DM-09** — As an agent user, I want one bounded DM synchronization cycle with a resumable cursor, so that a scheduler can retrieve new activity without rereading the entire inbox.
- **V01-DM-10** — As an agent user, I want newly observed DM activity emitted as a foreground NDJSON stream, so that a local service can react while knowing the stream is implemented by polling.

## Explicitly out of scope for v0.1

- Creating, drafting, editing, copying, publishing, reserving, activating,
  extending, promoting, marking sold, or deleting listings.
- Managing the user's own listings, seller inventory, paid placement, packages,
  or invoices.
- Platform offers, counteroffers, direct purchase, checkout, buyer protection,
  payment methods, payouts, identity verification, or transaction state.
- Shipping selection, labels, carrier integrations, tracking, returns, refunds,
  disputes, and tax reporting.
- Watchlist mutation, saved searches, alerts, seller following, recommendations,
  ratings, reports, blocking, and support tickets.
- Message attachments, automated responses, scheduled messages, bulk outreach,
  or sending without per-message confirmation.
- A required background daemon. A per-user daemon and MCP adapter are designed
  later layers; the v0.1 foreground poll/watch path must work without them.
- Structured pickup, meeting, negotiation, availability, payment-on-pickup, or
  offline transaction workflows; these remain opaque message text.
- Global or exhaustive username search.
- Any bypass of rate limits, access controls, bot challenges, or platform safety
  warnings.

The [full web user-story inventory](user-stories.md) remains as research and
traceability. Its inclusion of selling, payments, shipping, and other browser
features does not put those capabilities in kcli or v0.1.

## Release acceptance criteria

v0.1 is ready only when:

1. Written permission covers the intended automation, and an authorized live
   anonymous contract test proves location resolution, category metadata,
   common filters, every searchable metadata type/style in the release
   snapshot, pagination, detail, and one real image response.
2. Unknown metadata filters and listing fields are surfaced rather than silently
   discarded.
3. Seller lookup clearly distinguishes direct lookup from the local best-effort
   name index.
4. Two separately authorized dedicated test accounts prove login, token refresh,
   DM listing, DM reading, one confirmed reply, one confirmed first contact,
   warning handling, message receipt, and read-state handling.
5. No own-ad, shipping, payment, offer, transaction, pickup, meeting, or
   negotiation workflow is reachable from the application.
6. Every outbound message has an exact preview, explicit confirmation, one
   attempt, and an auditable local result without logging message contents or
   credentials.
7. Rate limiting defaults to at least 2.5 seconds between requests with jitter,
   and the client does not bypass `429` responses or access controls.
8. Human and JSON output contain stable IDs, official public URLs, source labels,
   and clear partial/unavailable states.
9. Documentation, tests, and [the changelog](../CHANGELOG.md) reflect the shipped
   behavior.
10. DM polling proves restart-safe, at-least-once delivery with stable event IDs,
    explicit cursors, bounded reconciliation, graceful interruption, and no
    duplicate send behavior. Default polling and watching are list-only and do
    not open conversations; watching clearly identifies itself as polling.
